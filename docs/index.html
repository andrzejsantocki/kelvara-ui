Technical overview

Kelvara documentation

Kelvara is an API-first Solana risk-intelligence system under development. This page defines the product direction without presenting unfinished capabilities as live.

Development notice. Kelvara is not yet a production monitoring service. Interfaces, thresholds, coverage, and service levels may change.

Overview

Solana protocols generate large volumes of on-chain state changes. Some events materially alter risk: a program is upgraded, a privileged authority changes, or liquidity moves outside its normal range. Kelvara's goal is to detect those events early, attach reproducible evidence, and deliver them in a form an operational team can use.

The intended users are security, risk, treasury, and protocol operations teams that need machine-readable monitoring without losing the underlying chain context.

Risk signals

Program upgrades

Monitor upgradeable programs for code deployment and related executable-state changes. A useful signal should identify the affected program, observed slot and time, relevant transaction, previous state, and resulting state.

Authority changes

Track changes to upgrade, administrative, mint, freeze, and other privileged authorities where coverage supports them. Severity should reflect the authority's capability and the protocol's declared operating model.

Liquidity anomalies

Compare liquidity and TVL observations against historical behavior. Detection should account for market movement, ordinary user flow, pool structure, and data quality before escalating an anomaly.

Evidence model

An alert without evidence creates more work. Each Kelvara signal is intended to carry enough context for independent verification:

  • stable signal identifier and versioned signal type;
  • network, slot, block time, accounts, and transaction signatures;
  • before-and-after values when they can be reconstructed reliably;
  • detection time, confirmation state, and data-source provenance;
  • confidence, severity, and explicit reasons for the classification.

Consumers should be able to follow references back to chain data rather than trust an opaque score.

Delivery model

The planned product is API-first. Candidate interfaces include a historical query API, webhooks for time-sensitive events, and a compact dashboard for investigation. Delivery guarantees and schemas will be documented before public availability.

InterfaceIntended role
APIQuery signals, entities, evidence, and monitoring state.
WebhooksDeliver signed, retryable event notifications to operational systems.
DashboardReview signal history and supporting evidence.

Operating principles

  • Evidence before assertion. Material claims link to verifiable observations.
  • Deterministic history. Reprocessing the same finalized chain range should produce explainable results.
  • Explicit uncertainty. Missing data and ambiguous classifications are surfaced, not hidden.
  • Low-noise defaults. Alert quality matters more than raw event volume.
  • Stable contracts. API and event schema changes are versioned.
  • Operational honesty. Coverage, latency, incidents, and limitations are documented.

Project status

Research and implementation are in progress. Public API access, network coverage, pricing, and service-level objectives have not been announced. This documentation will expand as interfaces become stable and verifiable.
